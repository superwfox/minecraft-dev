# 设计决策

记录项目中关键的技术选择和背后的原因。

## 为什么用 Cloudflare KV 而非 D1

| 对比项 | KV | D1（SQL） |
|--------|------|-----------|
| 数据模型 | 键值对，存 JSON | 关系表 |
| 适合场景 | 临时状态，TTL 自动清理 | 持久化业务数据 |
| 复杂度 | `put` / `get` / `delete` | 需要建表、写 SQL |
| 本地开发 | wrangler 内置 | 需要额外配置 |

生成任务是临时性的（1 小时后自动过期），不需要查询、关联或聚合。KV 的键值模型完全够用，且 TTL 自动清理免去了手动垃圾回收。

## 为什么逐文件生成而非一次性输出

一次性输出整个项目的问题：
- Token 限制可能截断输出
- 无法控制文件间的引用一致性
- 出错时只能全部重来
- 用户等待时间长且无反馈

逐文件生成的优势：
- 每个文件独立的 AI 调用，不受 token 上限影响
- 已生成文件的摘要作为上下文，保证 import 一致
- 单个文件出错可以 reChecker 返工，不影响其他文件
- 用户实时看到每个文件的生成进度

## reChecker 的跨文件审查策略

reChecker 现在接收已生成文件的结构化 API 摘要（类名、公开方法签名、事件、命令等），在审查当前文件时同时检查跨文件调用一致性。

这是对早期"无上下文审查"设计的演进。早期设计只检查单文件语法，跨文件一致性完全依赖 FileGen 的摘要机制。但实践中发现 AI 仍会"虚空调用"不存在的方法，单靠 FileGen 的约束不够。

当前设计的平衡点：

- **传入的是结构化摘要，不是完整代码**：每个已生成文件只传类名 + 公开方法签名 + 事件/命令列表，token 开销可控
- **双重防线**：FileGen 生成时约束"只能调用已列出的 API"，reChecker 审查时验证"调用的方法是否真的存在"
- **降级兜底**：如果摘要提取失败，reChecker 退回到纯单文件语法检查，不会阻塞流程

## 为什么用 workflow_dispatch 而非直接 SSH 编译

| 方案 | 优点 | 缺点 |
|------|------|------|
| workflow_dispatch | 零维护，隔离，免费 | 延迟较高（排队+启动） |
| 自建编译服务器 | 快 | 需维护 Java 环境，安全风险 |
| Cloudflare Workers 内编译 | 最快 | Workers 不支持运行 Maven |

GitHub Actions 的 2-5 分钟延迟对于"生成一个插件项目"的场景可以接受。用户不会频繁生成，而每次生成 AI 代码本身就需要 1-2 分钟。

## 为什么前端驱动而非服务端编排

服务端编排（一个 API 从头执行到底）的问题：
- Cloudflare Pages Functions 有 30 秒超时限制
- 整个流程可能需要 5-10 分钟
- 用户无法看到中间进度

前端驱动（按步调用 6 个 API）的优势：
- 每个 API 调用都在超时限制内完成
- 前端在每步之间更新 UI，用户实时看到进度
- 某一步失败可以重试，不需要从头开始
- KV 保存中间状态，刷新页面后可以恢复

## 为什么用独立仓库放 workflow

`minecraft-dev-workflow` 是一个独立仓库，而非在主仓库中创建分支：

- 主仓库是前端项目，不应该有 Java 代码的 commit 记录
- 独立仓库的临时分支不影响主仓库的 git 历史
- GitHub PAT 的权限可以精确控制到这一个仓库
